# 预编译 librust_lib_gitdeck.so 重编配方与复现验证

日期：2026-10-06（10-06 16:5x 补记：旧树清理 + 缓存自愈复验）　脚本：`scripts/rebuild_rust_so.sh`　关联提交：`da8cef5`（v1.5.12 TLS 修复）

## 结论先说

Android 侧 rust 引擎不再由 gradle 里的 cargokit 现场编译，改用入库的预编译产物：

```
rust_builder/android/src/main/jniLibs/arm64-v8a/librust_lib_gitdeck.so
sha256 = 7372dbfdada0e61e1a832c8d68d851db6eb40e7b3b36e09e4f9030657313f132（8914048 字节）
```

重编动作已收敛成一条命令。同一份源码在这台设备上 **11 次独立复现出逐字节相同的产物**，
其中包括一次 `touch` 强制 rustc 重编重链、一次**清空 target 目录从零冷编译**
（OpenSSL / libgit2 / libssh2 全部重新编译，8m45s）、以及一次**缓存实体被误删后 cargo 自愈重建**
（502s）—— 三种极端情况都逐字节命中（见 §4）。

## 1. 为什么是「预编译 so + 手工 build-gradle」这条路

- cargokit 的 gradle 插件把 rust 编译挂在 gradle 任务里，cc crate 的指纹会随
  gradle/PATH 等 env 翻滚；每轮全量构建都触发 sys 链（openssl 的 make 验证）重跑，
  单次 >600s，必然死循环（2026-10-03 实测三连）。
- 摘掉插件后（`rust_builder/android/build.gradle` 里 cargokit 的 `apply from` 与
  `cargokit { ... }` 块已注释），gradle 只负责「搬运 jniLibs」，整包构建回到分钟级。
- 代价：rust 侧改动必须手工重编 so 并提交那个二进制。本文件 + 脚本就是把这一步固化。

## 2. 配方（一条命令）

```sh
sh scripts/rebuild_rust_so.sh                 # 编到 /tmp/rbc-out/arm64-v8a/
sh scripts/rebuild_rust_so.sh /tmp/anywhere   # 编到指定目录
INSTALL=1 sh scripts/rebuild_rust_so.sh       # 编完并落 jniLibs（打印前/后 sha256）
sh scripts/build_apk.sh                       # 再出整包 APK
```

脚本做的事：备好一套固定的 `CARGOKIT_*` 环境，直接调 cargokit 的
`rust_builder/cargokit/run_build_tool.sh build-gradle`（即 gradle 插件本来会调的那条路），
再把产物从 `$CARGOKIT_OUTPUT_DIR/arm64-v8a/` 取出。

| 环境变量 | 值 |
| --- | --- |
| CARGOKIT_ROOT_PROJECT_DIR | 工程根 |
| CARGOKIT_MANIFEST_DIR | `<工程>/rust` |
| CARGOKIT_CONFIGURATION | `release` |
| CARGOKIT_TARGET_TEMP_DIR | `/tmp/gitdeck-cargokit-target` |
| CARGOKIT_TOOL_TEMP_DIR | `/tmp/gitdeck-cargokit-target`（复用已编译的 build_tool runner） |
| CARGOKIT_OUTPUT_DIR | 参数 1，默认 `/tmp/rbc-out` |
| CARGOKIT_TARGET_PLATFORMS | `android-arm64`（Flutter 平台名，**不是** `arm64-v8a`） |
| CARGOKIT_NDK_VERSION | `29.0.14206865` |
| CARGOKIT_SDK_DIR / COMPILE_SDK / MIN_SDK | `/opt/android-sdk` / `36` / `21` |
| CARGOKIT_JAVA_HOME | `/opt/jdk21/usr/lib/jvm/java-21-openjdk-arm64` |
| FLUTTER_ROOT / CARGO_NET_OFFLINE | `/opt/flutter` / `true` |
| SOURCE_DATE_EPOCH | `1791216077`（= 2026-10-05 16:01:17 UTC，见 §3-6） |

## 3. 六条「别改」的固定项（改任一项 = 字节变、或直接失败）

1. **`CARGOKIT_TARGET_TEMP_DIR` 固定 `/tmp/gitdeck-cargokit-target`**。
   该路径会被写进产物（libssl 的 `ENGINESDIR`/`MODULESDIR` 等），换路径就换字节；
   同时 openssl-sys / libgit2-sys / libssh2-sys 的已编译 C 依赖都缓存在这里，
   日常重编只重跑 rust 侧 + 重链，秒级到十几秒。
2. **CC shim 路径 `/tmp/cargokit-ndk-shim/clang`**。cargokit 每次构建自建这个 shim
   （`android_environment.dart` 里的确定性改动：符号链到 NDK 的 linux-x86_64 clang），
   并把 `CC_aarch64-linux-android` 指过去；OpenSSL 的 `compiler:` 字符串嵌的就是它。
   —— 顺带说明 NDK 是 x86_64 版、靠 box64 跑在 ARM64 设备上。
3. **`CARGO_NET_OFFLINE=true`**。本机对 crates.io 间歇 SSL reset，离线是唯一稳路径
   （124 个 crate 已在本地 registry）。
4. **FUSE 上 `run_build_tool.sh` 的 x 位是假的**，而 rustc 直接 exec 它当 linker
   （cargokit 把 `CARGO_TARGET_*_LINKER` 指成该脚本）。必须拷到 rootfs 加执行位再
   `mount --bind` 回来 —— 与 `scripts/build_apk.sh` 同一招，脚本里已内置。
5. **`CARGOKIT_TARGET_PLATFORMS` 要写 Flutter 平台名 `android-arm64`**。
   写成 ABI 名 `arm64-v8a` 会在 `build_gradle.dart` 的 `Target.forFlutterName` 抛异常，
   而且报错信息是误导人的 `Missing environment variable CARGOKIT_DARWIN_PLATFORM_NAME`
   （异常消息里那句 darwin 插值被 eager 求值）。
6. **`SOURCE_DATE_EPOCH=1791216077`（只在冷编译时起作用）**。
   产物里嵌着 OpenSSL 的 `built on: Mon Oct  5 16:01:17 2026 UTC` ——
   openssl 3.6.3 的 `util/mkbuildinf.pl` 取 `SOURCE_DATE_EPOCH`，缺省才用当前时间。
   不钉它，冷编译出来的产物就必然和入库那份差（只差这一个字符串所在的那几个字节）。
   脚本默认钉在首次入库那次 C 编译的时间上；热缓存命中（C 层不重编）时它不影响任何字节。

## 5. 复现边界（诚实说明）

- **产物里嵌了绝对路径与一个时间戳**，这就是「换机器/换目录能不能复现」的全部条件：
  - `/tmp/gitdeck-cargokit-target/...`（OpenSSL 的 `ENGINESDIR`/`MODULESDIR` 等）；
  - `/tmp/cargokit-ndk-shim/clang`（OpenSSL 的 `compiler:` 一行）；
  - `built on: ...`（由 `SOURCE_DATE_EPOCH` 决定，脚本已钉死）。
  三条都由脚本固定，所以**本机冷编译能字节复现**；但换机器复现仍要满足：
  同样的 NDK 版本 `29.0.14206865`、同样的 crate 版本（`openssl-src 300.6.1+3.6.3`、
  `libgit2-sys 0.18.8+1.9.7`、`libssh2-sys 0.3.3`…）、同样的 rustc（`stable` 1.98.1）
  和 `CARGO_NET_OFFLINE` 下的同一份 registry 源。
- **rust 源码一改，hash 必然变** —— 这是对的。脚本保证的是「同一份源码复现同一份字节」，
  不是「永远同一个 hash」。
- 该 `.so` 是**未 strip** 的（8.9MB，带 debug 段）；gradle 打包时再做
  `stripReleaseDebugSymbols` → 包内 7.2MB。所以「jniLibs 的大小」和「APK 里的 .so 大小」
  不一样是正常的，别拿 APK 里的去对 hash。
- `/tmp/gitdeck-cargokit-target` 现在是 **253MB** 的干净树，就是唯一的热缓存
  （§4 第 11 条 4.3s 命中，悬空符号链接数为 0）。旧的那棵 2.4GB（含 x86_64 / i686 / debug
  的实验残留）已于 10-06 16:40 删除，**释放 2.2GB**。

### 5.1 一个真踩到的坑：在 PRoot 下 `rm -rf` 会连带删掉另一棵树共享的 l2s 实体

删那棵旧树时踩到一条**不是常识能推出来的**行为，记下来免得重蹈：

- 那棵旧树的条目是 PRoot 的 **l2s 符号链**：`.l2s.<name>0001` 是**实体**，`<name>` 是指向它的
  符号链接；而且部分链接**指回标准路径** —— 两棵树在 PRoot 的硬链接账本里是**同一批名字**。
- 于是 `rm -rf` 旧树时，PRoot 把共享的 `.l2s.*` 实体一起删了：标准树的
  `deps/.l2s.librust_lib_gitdeck.so0001` 等实体消失，只剩悬空符号链接；
  `du` 从 253MB 掉到 181MB，`stat` 那些 `.l2s.*` 报 ENOENT。
  （`rm` 是 GNU coreutils 9.4，**不跟随符号链接** —— 这是 PRoot 硬链接模拟的账本问题，不是 rm 的锅。）
- **后果可控且自愈**：cargo 发现实体缺失就重建，一次 502s 的构建把缓存补齐（§4 第 10 条），
  产物**依旧逐字节一致**；现在 `find -type l` 的悬空链接数为 **0**。
- 教训：**在这个环境里，别 `rm -rf` 一棵与你在意的树共享 l2s 链接的树。**
  要清就先让两棵树彻底分开（或 `cargo clean` 后整棵重建），别指望 `rm` 只删自己那一份。

## 6. 纪律（改 rust 后的固定动作）

1. `INSTALL=1 sh scripts/rebuild_rust_so.sh` —— 重编并落 jniLibs；
2. 提交那个二进制（`jniLibs` 入库是刻意的：CI 与他机不重编 rust）：
   `git add rust_builder/android/src/main/jniLibs/arm64-v8a/librust_lib_gitdeck.so`；
3. 提交信息里写明「重编 librust_lib_gitdeck.so」，并附新 hash（便于日后核对是否漂移）；
4. 再 `sh scripts/build_apk.sh` 出整包。
