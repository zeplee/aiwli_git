## 1. 问题不是「漏加了转圈」，是设计上不存在可显示的中间事实

用户反馈：点「推送提交」后等待过程没有任何反应，不知道正在发生什么。

查完代码，这是**四层结构共同决定的必然结果**，不是 UI 疏忽：

| 事实 | 位置 | 后果 |
|---|---|---|
| `push` 是同步阻塞函数，返回 `Result<String, String>` | `rust/src/api/ops_remote.rs:389` | Rust 侧跑完才有返回值 |
| `PushOptions` 只挂了认证回调，**没有 `transfer_progress` / `sideband_progress`** | 同上 `:417` | 连「传了多少对象」都没采集 |
| 通道是 `Isolate.run(() => _callSync(...))`——一次性请求/响应 | `lib/engine/ffi.dart:315` | 中间状态**无处可传** |
| `runSync` 从 `await engine.push(...)` 到 `showSnack` 之间零状态变更 | `lib/pages/sync_flow.dart`（旧版 `:112-133`） | UI 无事可做 |

⇒ 在「按下」和「拿到结果」之间，程序里**不存在**任何可显示的中间事实。

## 2. 顺手挖出一个真 bug：推送期间按钮仍可点

`lib/pages/workbench_page.dart` 里其实**已经有进度条**：

```dart
if (_busy) const LinearProgressIndicator(minHeight: 2),   // 旧版 :1187
```

但 `_busy` 只在 `_reload` / `_commit` 里被设置，**`runSync` 从不碰它**。而按钮是
`onPressed: _busy ? null : …` → **一次推送可以点出多次**。

实测证据：排障时连点两次，`gitdeck_error.log` 真的出现两条 `push` 记录；
第二次的链路抖动（`SSL error: unknown error; class=Ssl (16)`）当时还被误判成了
证书问题（见 docs/15 第六节）。**并发推同一分支不只浪费，还会污染故障归因。**

## 3. 状态模型：一个状态机，不是一个布尔量

```
idle → running(phase) → success | failed | notice → idle
```

- `running`：常驻操作条，带**阶段文字**与**已用时间**；
- `success`：自动淡出（4s）——低信息量且可自证；
- `failed`：**常驻**直到用户处理或重试。错误不该 4 秒就消失（1.5.18 实测：
  4 秒的合并徽标，读屏慢一点就已经没了）；
- `notice`：中性——操作没执行但不是错误（如用户未接受 SSH 主机指纹）。

关键在 **`phase` 本身就是诊断信息**：卡在「读取远程列表」指向配置/路径，
「检查 SSH 主机」指向 known_hosts，「连接远程并上传」指向网络/代理。
这比事后解析错误文本可靠——阶段是我们**自己调的步骤**，不需要靠猜。

## 4. 四层反馈

| 层 | 时机 | 载体 |
|---|---|---|
| L0 即时 | <100ms | 按钮 disabled + 操作条立刻出现 |
| L1 过程 | 秒级 | 阶段文字 + `已用 Ns` + 2px 细进度条 |
| L2 终态 | 完成时 | 成功自隐 / **失败常驻** + 重试 + 详情 |
| L3 事后 | 事后 | 本轮**未做**（见 §7） |

**「已用 Ns」不可省**：它是「没卡死」的唯一证明。没有它，用户无法区分「慢」和
「死了」——本次排障时我盯着 `gitdeck_error.log` 猜了三分钟，就是在人工替代它。

## 6. 三条设计约束（都是从这次复盘里长出来的）

1. **不假装知道引擎内部进度**。折叠态不写「正在连接…」这种我们其实不知道的
   话；阶段粒度止于调用边界，`docs` 与 CHANGELOG 都如实标注。
2. **人话与证据分开**。折叠态只放人话（新增纯函数 `shortReason` 剥掉
   `（原始：…）` 尾巴），原始错误放到「详情」——且是**未截断**的完整串
   （`friendlyError` 只保留 240 字，真因常在截断之外），用 `SelectableText`
   以便长按复制原样发出来。
3. **不变量由结构保证，不靠人记**。`runSync` 用 `try/finally` 兜底：
   任何提前 return（用户取消、目标未就绪）都不允许把操作条永久留在「进行中」
   ——否则按钮会被一起锁死，变成新的「点了没反应」。

### 反例（明确不做）

- ❌ **模态遮罩转圈**：操作可能几十秒，遮罩让用户没法翻 diff、没法复制信息，
  系统返回键行为也尴尬；
- ❌ **把 snackbar 从 4s 改成 10s**：治标，且长时间遮挡内容；
- ❌ **假进度条**（定时器 0→90%）：一旦停在 90% 卡住，比没有进度更糟；
- ❌ **没有取消能力就放「取消」按钮**：假取消比没有更伤信任。

## 7. 尚未做：L3「最近操作」

原设计里第 4 层是「最近操作」列表（时间/操作/结果/耗时/原始错误）。
本轮**没做**：失败终态已常驻，重开 App 前的历史仍会丢。
后续若要补，建议与 P2 的 `phase` 一起上——那时每条记录能带真实的
连接/认证/传输耗时，才真正可用来判断「是不是每次都卡在第 3 步」。

### ⚠️ 方法论教训：中文串必须按 UTF-16 验

第一次按 UTF-8 `grep` 校验，**7 个新串全部 0 命中**，差点误判成「改动没编进包」。
实际原因是 **Dart AOT 把非 ASCII 字面量按 UTF-16LE 存**——连旧版早就存在的
`推送提交` 也是 `utf8=0 / utf16le=2`。

上轮（docs/15）校验 `class=ssl`、`resolve address` 之所以顺利，是因为那些串
**恰好是纯 ASCII**。所以这条判据要写成：

> 校验包内特征串，**中文按 UTF-16LE、ASCII 按 UTF-8**；两者都要先拿一个
> **旧版已存在的串做基线**，确认方法本身有效，再看新增串的 0/1 差异。

拿「0 命中」直接下结论，等于用一个未验证的尺子量长度。

## 10. 相关观察：仓库与远端已完全同步

排查用户「提交到远程还是没成功」时，仓库侧证据（`/mounts/Projects/aiwli_git`）：

- `main` = `origin/main` = `7eb1ef0`，工作区干净，**没有任何待推送的提交**；
- `refs/remotes/origin/main` reflog 有 4 条 `push: update remote tracking`
  （该引用只在远端接受后才写），最后一条时间戳 `1791380737`；
- 远程是真实 HTTPS（`https://github.com/zeplee/aiwli_git.git`；
  `api/repos → 404` 私有、`info/refs → 401` 需认证）；
- `.git/` 今日唯一的写入是 `.git/index`（18:05，**是我自己跑 `git status`** 触发的），
  **没有 App 侧的仓库写入**。

⇒ 用户遇到的失败**不是「提交没到远端」**。在没有设备日志的前提下，最可能的
方向是 App 侧无法读取/操作该仓库（例如更新安装或重启后「所有文件访问」被重置，
`friendlyError` 里有对应分支 `isStorageDeniedError`），或是又一次链路抖动。
本轮做的操作条正是为这类问题准备的仪器：它会在**失败前**就告诉我们在哪一步，
并把未截断的原始错误交到用户手上。
