# v1.5.13 — Android HTTPS 信任锚修复、自签 CA 导入与校验逃生口

日期：2026-10-07　关联版本：`1.5.13+24`　关联问题：clone / fetch / push / pull 一律
`the SSL certificate is invalid`（`GIT_ERROR_SSL` / `class=Ssl 16`）

## 0. 结论先说

| 问题 | 结论 |
| --- | --- |
| v1.5.12 的修法（`set_ssl_cert_dir` 指向 Android 系统库） | **完全无效**，且因为「加载成功」的假象而**静默失败** |
| 正确修法 | 把系统库的 PEM **拼成 bundle 文件**，用 `set_ssl_cert_file` 加载 |
| 部分同类客户端为什么能用 | 它们把证书校验**整个关掉**（`certificate_check` 无条件返回 `CertificateOk`），所以从来不需要 CA 库 |
| 自签证书的仓库 | 导入其 CA（**校验保持开启**）；「跳过证书校验」开关是最后手段，默认关闭 |

---

## 1. 根因：两个独立的坑叠在一起

### 1.1 `set_ssl_cert_dir` 在 Android 上是死路（哈希算法不匹配）

- Android 系统信任库的文件名是 **`MD5(subject)`**（`openssl x509 -subject_hash_old`）。
- OpenSSL >= 1.0 的哈希目录查找器按 **`SHA1(subject)`**（`subject_hash`）去找 `<hash>.0`。
- 实测量化（同一台设备、130 张系统 CA）：
  - 命中 `subject_hash_old`（MD5）：**130 / 130**
  - 命中 `subject_hash`（SHA1）：**0 / 130**

→ 查找时**永远找不到任何证书**。

### 1.2 更隐蔽的一半：`SSL_CTX_load_verify_locations` 带目录时是**惰性**的

它只登记一个哈希目录查找器就返回 1，**不检查目录里有没有证书**。所以
`git2::opts::set_ssl_cert_dir(dir).is_ok()` **恒为真** —— 代码看起来「加载成功」，
实际信任锚是 0，失败被推迟到握手阶段。

**这两条合起来解释了这个 bug 为什么能活这么久**：既没有明显报错，也没有可疑返回值，
唯一的症状是远程操作报一句笼统的 SSL 错误。

### 1.3 实测对照（同一台设备、同一 OpenSSL）

| 做法 | `openssl s_client` 结果 |
| --- | --- |
| 原样 `set_ssl_cert_dir(/system/etc/security/cacerts)` | `Verify return code: 20 (unable to get local issuer certificate)` |
| 拼成 PEM bundle + `set_ssl_cert_file` | **`Verify return code: 0 (ok)`** |

## 2. 为什么部分同类客户端「能连上」——不是修好了，是**没在校验**

某同类客户端的实现（`get_default_callbacks()` 内，**无条件**执行）：

```rust
callbacks.certificate_check(|_, _| Ok(CertificateCheckStatus::CertificateOk));
```

链路（libgit2 源码级）：

1. `streams/openssl.c` 的 `verify_server_cert` 先判 `SSL_get_verify_result`；
   因为信任锚为 0（同一台设备、同样是 vendored OpenSSL、同样找不到 CA），
   它返回 `GIT_ECERTIFICATE`。**这一步在回调之前就发生了。**
2. `transports/httpclient.c` 的 `http_server_connect`：

   ```c
   error = git_stream_connect(server->stream);
   if (error && error != GIT_ECERTIFICATE)   // ← GIT_ECERTIFICATE 被吞掉，不返回
       return error;
   if (git_stream_is_encrypted(server->stream) && cert_cb != NULL)
       error = check_certificate(server->stream, &server->url, !error, cert_cb, cb_payload);
       //                                                        ↑ is_valid = !error = 0
   ```

3. `check_certificate` 内：`if (error == GIT_PASSTHROUGH) error = is_valid ? 0 : -1;`
   → 回调返回 `CertificateOk` 即**继续连接**（即使证书无效）。

**对照结论**

| | 回调返回 | libgit2 行为 | 结果 |
| --- | --- | --- | --- |
| 部分同类客户端 | `CertificateOk` | 吞掉 `GIT_ECERTIFICATE` 后直接放行 | 能连上，**完全不校验** |
| 本工程（本次修改前） | `CertificatePassthrough` | `is_valid(0) ? 0 : -1` → `-1` | 状态正确，但信任库没接上 → 报错 |

即：**方向一直是对的（想要校验），缺的是信任锚**。修法是补上信任锚，
而不是把校验关掉。

### 2.1 一个附带事实：部分客户端的「按仓库开关」是空转

它还实现了 `get_disable_ssl` / `set_disable_ssl`（读写 `http.sslVerify`），
但 **libgit2 全源码里没有任何地方读这个配置**（`src/` 全量 grep 零命中）。
真正生效的只有那个**无条件**的 `CertificateOk`。

## 3. 为什么不能靠 `certificate_check` 回调做「真校验」

libgit2 的 `streams/openssl.c` 用
`X509_get_peer_certificate` + `i2d_X509` 把证书交给回调 —— **只给叶子证书，没有中间证书**。
拿不到链就重建不了链，回调只能「放行 / 拒绝」，而「放行」就等于第 2 节那条无校验的路。

→ 信任锚**必须在握手之前**准备好。这正是「拼 bundle」的位置。

## 4. 最终设计（三级，默认全安全）

| 级 | 做什么 | 默认 | 覆盖谁 | 实现位置 |
| --- | --- | --- | --- | --- |
| 1 | Android 系统 CA → PEM bundle → `set_ssl_cert_file` | **开启** | 正规证书的仓库（GitHub / GitLab / 云效…） | `util::init_tls_inner` |
| 2 | 导入自签 / 内网 CA，拼进**同一个** bundle | 空 | 自签证书的仓库（**校验仍开启**） | `util::ca_import` |
| 3 | 跳过 TLS 证书校验（逃生口） | **关闭** | 代理拦截等兜底 | `util::skip_tls_verify` + `ops_remote::x509_verdict` |

**bundle = 系统 CA + 用户导入的 CA**，一次 `set_ssl_cert_file` 两者都进去。

### 4.1 关键实现细节

- **落盘位置必须显式传入**：App 进程的 `TMPDIR` / `HOME` 都是空的，
  `std::env::temp_dir()` 会退到并不存在的 `/tmp`。Dart 侧 `main()` 启动时把
  `getFilesDir()` 经 `setCaDir` 交给 Rust；Rust 侧还有一条兜底
  （从 `/proc/self/cmdline` 反推 `/data/data/<pkg>/files`）。
- **不能用 `Once`**：`Once::call_once` 一旦执行过，即使失败也不会重试 ——
  首次失败会把整个进程**永久锁在信任锚为 0** 的状态。改为「**成功才缓存**」
  （`TLS_APPLIED`），失败下次自动重试。
- **导入 CA 立即生效**：`set_ssl_cert_file` 是**追加**语义（往同一个 `SSL_CTX` 的
  store 里加），所以导入后当场生效、无需重启。
- **删除 CA 需重启**：同一个原因的反面 —— OpenSSL 的 store **只能加不能减**，
  删文件后当前进程的信任集不变。UI 上明确写了这一点（否则用户以为删掉了其实还在信任）。
- **单个用户 CA 文件格式**：`# label: 名称` + 若干 PEM 块。PEM 解析器只看
  `BEGIN/END` 之间的内容，所以标签行不影响校验，省掉一个索引文件。
- **逃生口只作用于 HTTPS/X.509**：`make_callbacks` 里 SSH 走的是 hostkey 分支
  （known_hosts 的 Match / Mismatch / Unknown 逻辑），开关加在
  `cert.as_hostkey() == None` 那个分支上，**不动 SSH 的信任流程**。
- **原始错误必须保留**：旧实现用提示文案**整个替换**掉 libgit2 的错误，
  于是真正的 `the SSL certificate is invalid` 永远看不到 —— 这次定位问题的成本
  基本都花在这上面。改为在原始错误**之后追加**提示。

1. 启动 App 后，`<appFilesDir>/gitdeck_ca_bundle.pem` **应当存在**
   （旧实现只调 `set_ssl_cert_dir`，不落任何文件 → **这个文件的存在本身就是
   「新代码在跑」的铁证**）。
2. 设置 →「网络安全」应显示信任库状态（系统库路径 / 证书数 / bundle 路径）。
3. 对 GitHub 这类正规证书的仓库做 fetch / push → 应成功（且是**真校验**）。
4. 导入一个自签 CA 后，对该自签仓库 fetch → 应成功，且开关仍是「校验已开启」。

### 6.4 信任库诊断（`gitdeck_ca_diag.txt`）与一个真实案例

App 每次重建 bundle 都会把**逐目录扫描明细**落到
`<appFilesDir>/gitdeck_ca_diag.txt`，同一内容也显示在「设置 → 网络安全」：

```
bundle=/data/user/0/com.aiwli.git/files/gitdeck_ca_bundle.pem
证书总数=129 跳过=0
/system/etc/security/cacerts: 条目=129 文件=129 读取失败=0 无证书=0 证书=129
/data/user/0/com.aiwli.git/files/gitdeck_user_ca: 条目=0 文件=0 读取失败=0 无证书=0 证书=0
跳过校验=false
```

**这个诊断不是装饰 —— 它当场解决过一个真实问题。** 本机实测出现
「root 数得到 130 个 CA 文件、bundle 只有 129 张」，逐项排查：

| 排除项 | 证据 |
| --- | --- |
| 文件损坏 | 该文件 BEGIN@0 / END@1792、无 CR / BOM / NUL、标准 64 列换行、合法 UTF-8、零非 ASCII |
| 权限 | 目录内 130 个文件全是 `-rw-r--r--`；以 App 的 uid（`u0_a661`）`cat` 得到 130 |
| SELinux | 130 个文件标签**完全相同**（`u:object_r:system_security_cacerts_file:s0`），目录标签也一致 |
| 解析丢块 | 该证书的 base64 主体在 bundle 里做**子串**检查 = 不存在；bundle 中也没有等长块 |
| 我的去重 / 读取 | 诊断显示 `条目=129 读取失败=0 无证书=0` → **App 的 `read_dir` 只列出 129 个** |

成因：那张 CA 是 **`reqable-magisk` 模块**注入的（Reqable 官方的「把抓包 CA 装进系统
信任库」模块，文件在 `system/etc/security/cacerts/3e3af00e.0`，subject 为
`O = Reqable, LLC` / `CN = Reqable CA`，自签根 `CA:TRUE`）。Magisk 的模块挂载
**在 `su` 的命名空间里可见**（`su -c` 与 `su -mm` 都数到 130），
**App 进程的命名空间里没有** → App 看到的是未注入的 129 张。

**结论：代码没有丢证书，是 App 的视图里本来就没有它。**
这也是把「读取失败 / 无证书」计数写进诊断的原因 —— 否则「129 vs 130」永远说不清。

> **对用户的直接含义**：如果依赖代理抓包（Reqable / Charles / mitmproxy …），
> **单靠这类 Magisk 模块注入系统库，App 未必看得到那张 CA**（本机实测就是看不到）。
> 正确做法是用「设置 → 网络安全 → 导入」把该 CA 的 PEM 导进来（**校验保持开启**），
> 而不是去关校验。Reqable 的 CA 在本机路径为
> `/data/adb/modules/reqable-magisk/system/etc/security/cacerts/3e3af00e.0`。

## 7. 风险与边界（明确写清）

- **打开逃生口 = 放弃服务器身份核对**。公共 WiFi、被劫持的 VPN / 代理上的攻击者
  可以冒充 GitHub，**代码与访问令牌可能被窃取，而且推送会「看起来成功」**。
  默认关闭；开启需二次确认，UI 常驻红色警示；能用上第 2 级（导入 CA）就别用它。
- **代理抓包的 CA 必须显式导入**：见 6.4 的实例 —— 系统库里有、App 的视图里**不一定有**
  （Magisk 模块挂载在 App 进程的命名空间里可能不存在）。用代抓包却连不上时，
  先按「设置 → 网络安全」的信任库状态判断，再决定是导入 CA 还是走 SSH。
- **导入 CA 是「扩大信任面」**：只导入你确实要信任的那个 CA，不要图省事导入来路不明的证书。
- **删除已导入的 CA 需重启应用**才彻底生效（OpenSSL store 只能加不能减）。
- **中间证书不被回调暴露**（第 3 节），所以第 2 级是自签场景的**唯一正解**，
  不是"更麻烦的等价做法"。
- 未采用的其他路线，以及为什么：`set_ssl_cert_dir` 死路（第 1 节）；
  `git_stream_register_tls` 要自己实现整个 TLS 流接口（不现实）；
  换 mbedtls 后端（其 `parse_path` 逐文件解析、不看文件名哈希，目录方案反而能用，
  但换 TLS 后端是大动作）；`rustls-platform-verifier` 属 rustls 生态，
  与 libgit2 的 OpenSSL 后端接不上（libgit2 没有"换平台验证器"的插槽）。

## 8. 复现命令速查

```sh
# 1) 观察系统库命名算法（证明 MD5 而非 SHA1）
for f in /system/etc/security/cacerts/*; do
  openssl x509 -in "$f" -noout -subject_hash_old -subject_hash 2>/dev/null
done | sort | uniq -c | head

# 2) 对照实验：目录 vs bundle
openssl s_client -connect github.com:443 -CApath /system/etc/security/cacerts </dev/null 2>&1 | grep "Verify return code"
cat /system/etc/security/cacerts/* > /tmp/b.pem
openssl s_client -connect github.com:443 -CAfile /tmp/b.pem </dev/null 2>&1 | grep "Verify return code"

# 3) 本工程重编 + 出包
INSTALL=1 sh scripts/rebuild_rust_so.sh
sh scripts/build_apk.sh
```
