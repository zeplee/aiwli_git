# 14 · v1.5.17：HTTPS 信任锚的真根因（no-stdio）与内存注入修复

> 结论先行：**vendored OpenSSL 是 `no-stdio` 构建**，导致 libgit2 里**任何「从文件加载 CA」的方式都必然失败**。
> 1.5.12 的 `set_ssl_cert_dir`、1.5.13 的 `set_ssl_cert_file`、以及本轮的「逐文件加载回退」全部无效。
> 唯一可用的是**内存注入**：PEM → `PEM_read_bio_X509` → `GIT_OPT_ADD_SSL_X509_CERT`。

---

## 1. 现象

用户截图：界面底部红色横幅 `网络连接失败：请检查网络后重试。`（版本 1.5.13）。

而 1.5.13 的 CHANGELOG 声称「真正修好 HTTPS 远程」。**两者矛盾 —— 说明 1.5.13 的验收有缺口。**

---

## 2. 第一步：真因被"吞"了两层

### 2.1 UI 层：证书错误被误报成网络错误

`lib/widgets/dialogs.dart` 的 `friendlyError` 里，网络分支的关键字表含**裸 `'网络'`**；

而 `rust/src/api/ops_remote.rs` 的 `transport_hint` 在证书校验失败时会**追加**一段提示：

```
提示：HTTPS 证书校验失败。已自动加载 Android 系统信任库（设置 → 网络安全 可查看状态）；…
                                                     ^^^^^^ 命中裸 '网络'
```

**于是任何证书失败都被显示成"网络连接失败"。自己写的提示文案污染了自己的分类器。**

修复：证书判定提到网络之前、去掉裸 `'网络'`、三类错误都附上**原始错误**。

### 2.2 引擎层：`init_tls` 的失败被静默丢弃

```rust
pub fn init_tls() {
    let _ = init_tls_inner();   // 失败即丢
}
```

且 `set_ssl_cert_file` 的返回值从未被记录 —— 所以「看起来正常」与「实际失败」在代码里长得一样。

修复：`record_error` 把每个 `dispatch::call` 的错误落盘到 `<appFilesDir>/gitdeck_error.log`（含 libgit2 的 `class=/code=` 与当时 TLS 状态）。

## 3. 逐步排除（全部实测）

| 假设 | 判据 | 结论 |
|---|---|---|
| 网络不通 | 容器 `curl https://github.com/…` → `code=401 verify=0` | 排除（TLS 通过，401 是私有库缺认证） |
| 代理/VPN 干扰 | `settings get global http_proxy` = null；`dumpsys connectivity` 无 VPN 网络 | 排除 |
| 系统 CA 库损坏 | 用 App 生成的 bundle：`code=401 verify=0`；含 USERTrust RSA 等 129 张 | 排除 |
| HTTPS 没编进 libgit2 | 编译产物 `git2_features.h`：`GIT_HTTPS 1` / `GIT_OPENSSL 1` | 排除 |
| 路径/权限/SELinux | 引擎自检 `回读 bundle: 200313 字节 ok` | 排除 |
| **文件加载机制本身** | **逐文件加载 129 个系统证书 → 129/129 全失败** | **← 命中** |

关键诊断输出（`gitdeck_ca_diag.txt`）：

```
· 回读 bundle: 200313 字节 ok
· bundle 一次性加载失败: OpenSSL error: failed to load certificates: error:05880020:x509 certificate routines::BIO lib; class=Ssl (16)
· 回退逐文件加载: 成功 0 · 失败 129
· 首个失败: /system/etc/security/cacerts/b936d1c6.0: … BIO lib
```

**129 个世界可读的系统文件全部打不开 ⇒ 不是路径问题，是 OpenSSL 的文件 BIO 不可用。**

---

## 4. 根因：`OPENSSL_NO_STDIO`

vendored OpenSSL（openssl-src）生成的配置头：

```c
/* …/openssl-sys-*/out/openssl-build/install/include/openssl/configuration.h */
# ifndef OPENSSL_NO_STDIO
#  define OPENSSL_NO_STDIO        // ← 定义即禁用 stdio
# endif
```

**OpenSSL 内部没有 `fopen` 通路。** 对应到代码：

- `crypto/x509/by_file.c`：`BIO_new_file(file,"r")` 返回 NULL → `ERR_raise(X509, ERR_R_BIO_LIB)` → 经 libgit2 包装成
  `failed to load certificates: … BIO lib`（就是界面/日志里那句）
- 因此连它自己的默认路径加载 `X509_STORE_set_default_paths`（读 `/usr/local/ssl/cert.pem`）也只是"没证书"，
  libgit2 的 `git__ssl_ctx` 仍然建得起来，但**信任锚是 0**。

这也顺带解释了 docs/13 里"目录方式静默无效"的观察：目录查找器同样是基于文件的。

---

## 5. 修复：内存注入

libgit2 提供了不碰文件的入口（`settings.c`）：

```c
case GIT_OPT_ADD_SSL_X509_CERT:
#ifdef GIT_OPENSSL
    { X509 *cert = va_arg(ap, X509 *); error = git_openssl__add_x509_cert(cert); }
```

而 `git_openssl__add_x509_cert` 是纯内存操作：

```c
if (!(cert_store = SSL_CTX_get_cert_store(git__ssl_ctx))) return -1;
if (cert && X509_STORE_add_cert(cert_store, cert) == 0) { … }
```

实现（`rust/src/api/util.rs`）：

```rust
BIO_new_mem_buf(pem) → 循环 PEM_read_bio_X509 → git_libgit2_opts(45, x) → X509_free
```

`git_libgit2_opts` 是 variadic，bindgen 不生成绑定，故手写声明。**选项值 45 用 gcc 从 libgit2 头文件求值确认**：

```
$ gcc -I libgit2/include … && ./optval
ADD_SSL_X509_CERT=45  SET_SSL_CERT_LOCATIONS=12
```

## 6. 途中的坑（1.5.16 崩溃）

第一次上内存注入后**冷启动即 SIGSEGV**：

```
signal 11 (SEGV_MAPERR), fault addr 0x28, Cause: null pointer dereference
#06 … base.apk (gitdeck_call+448)     线程 DartWorker
```

原因：`GIT_OPT_ADD_SSL_X509_CERT` 访问 libgit2 内部的 `git__ssl_ctx`，而它由
`git_openssl_stream_global_init()` 在 **`git_libgit2_init()`** 时创建。
`git2::opts::*` 内部会先 `crate::init()`，所以走封装是安全的 —— **手写的 FFI 调用没有这一步**。

而启动时 Dart 的顺序是：`setCaDir`（→ `tls_json` → `init_tls_inner`）**先于** `openRepo`（→ 首次 git2 调用），
此时 `git__ssl_ctx` 还是 NULL → `SSL_CTX_get_cert_store(NULL)` → 空指针解引用（`0x28` 正是该成员偏移）。

**修复：调用前先 `git_libgit2_init()`（幂等）。**
教训：**手写 FFI 会绕过封装层隐含的前置条件**；崩溃点在启动路径，第一次就能暴露，属于幸运。

## 7. 验证链

| 环节 | 结果 |
|---|---|
| gcc 求值枚举 | `ADD_SSL_X509_CERT=45` |
| 引擎自检（真机） | `回读 bundle: 200313 字节 ok` / **`内存注入 X509: 加入 129/129 张`** |
| 设置页「网络安全」 | `信任库状态：bundle=/data/user/0/com.aiwli.git/files/gitdeck_ca_bundle.pem 跳过校验=false` |
| 冷启动 | 不再崩溃（1.5.16 崩溃 → 1.5.17 正常） |
| 远程操作错误类别 | `class=Ssl (16)`（证书）→ **`class=Os (2)`**（网络层） |

最后一条是重要的间接证据：**证书校验阶段不再报错**。

## 8. 遗留：当前网络的境外阻断（与 App 无关）

同一时刻容器实测：

| 站点 | 结果 |
|---|---|
| gitee.com / aliyun.com / codeup.aliyun.com | `200 / 403 / 302`，`verify=0` |
| **github.com / google.com** | **`code=000`（`Recv failure: Connection reset by peer`，`connect` 仅 39ms）** |

TCP 连得上、TLS 握手被 RST —— 典型的 SNI 阻断。App 的错误与容器完全一致。

**⇒ 「libgit2 在可达网络上完成 TLS 并成功 fetch」这一步，需要在网络可达（或开代理）时做最终确认。**
App 侧已具备条件（信任锚 129/129 就位、校验保持开启）。

## 9. 复现命令

```sh
# 1) 编译期事实：no-stdio
grep -n 'OPENSSL_NO_STDIO' \
  /tmp/gitdeck-cargokit-target/aarch64-linux-android/release/build/openssl-sys-*/out/openssl-build/install/include/openssl/configuration.h

# 2) 枚举值（权威）
gcc -I <libgit2-sys>/libgit2/include -o /tmp/optval - <<'EOF' && /tmp/optval
#include <stdio.h>
#include "git2.h"
int main(void){ printf("%d\n",(int)GIT_OPT_ADD_SSL_X509_CERT); return 0; }
EOF

# 3) 重建引擎产物（no-stdio 之外，其余路径固定，可字节复现）
sh scripts/rebuild_rust_so.sh

# 4) 真机自检（需 root）
adb shell su -c 'cat /data/user/0/com.aiwli.git/files/gitdeck_ca_diag.txt'
adb shell su -c 'cat /data/user/0/com.aiwli.git/files/gitdeck_error.log'
```
